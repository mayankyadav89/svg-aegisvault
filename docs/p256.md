# secp256r1 / P-256

## Identity

- secp256r1 = P-256 = prime256v1 (CONFIRMED)
- Distinct from secp256k1 (CONFIRMED)

## Domain parameters (from RIP-7212 / EIP-7951)

- Prime field `p = 0xffffffff00000001000000000000000000000000ffffffffffffffffffffffff`
- Equation: `y^2 = x^3 + ax + b (mod p)`
- `a = 0xffffffff00000001000000000000000000000000fffffffffffffffffffffffc`
- `b = 0x5ac635d8aa3a93e7b3ebbd55769886bc651d06b0cc53b0f63bce3c3e27d2604b`
- Generator `Gx = 0x6b17...c296`, `Gy = 0x4fe3...51f5`
- Order `n = 0xffffffff00000000ffffffffffffffffbce6faada7179e84f3b9cac2fc632551`
- Cofactor `h = 1`

## ECDSA semantics

- Signature components `(r,s)` must be in `(0,n)` for precompile acceptance (CONFIRMED).
- Public key `(x,y)` must be on-curve and bounded by field modulus checks (CONFIRMED in RIP-7212/EIP-7951).
- EIP-7951 explicitly states no mandatory non-malleability/low-S rule at precompile layer (CONFIRMED).

## Important distinction

- secp256k1 assumptions (e.g., Ethereum EOA recovery behavior) must not be reused for P-256 verification paths (CONFIRMED).
